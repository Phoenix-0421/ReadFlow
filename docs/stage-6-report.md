## 二、发现的问题及其原因

### 2.1 已修复（5 个）

**问题 1：导航栏「书籍详情」指向假 id，点进去必然报错**

- 现象：点导航第 4 项 → 进入 `/books/demo` → 显示「没有找到这本书」。
- 原因：第一阶段为了让 `/books/:id` 这条动态路由能被手动打开验证，加了一个固定占位链接。当时详情页还没有真实数据，注释里也写了"先用一个固定的占位地址"。**现在详情页已经有真实入口（书籍卡片）了，这个链接就只剩副作用**。
- 影响：四个导航入口里有一个必然走到错误页，属于明显的体验缺陷。

**问题 2：书架里的书进不去详情页，尤其是「想读」状态的书**

- 现象：详情页（阅读进度和笔记的**唯一**编辑入口）只能从首页的「正在阅读」「最近读完」点进去。
- 原因：第三阶段给书架卡片加的是状态下拉框和删除按钮，没加详情链接；第五阶段给首页加了 `to` 链接，但书架没同步。
- 影响：**「想读」状态的书在首页完全不出现**（首页只有 reading 和 finished），所以这类书的详情页实际上只能靠手输 URL 才能打开。这是真实的功能死角。
- 补充：这也是为什么问题 1 不能只删链接了事 —— 必须在书架补上真实入口。

**问题 3：损坏的 localStorage 原文会被后续写入覆盖，没有任何备份**

- 现象：数据损坏时应用会按空书架启动并给出提示（这部分原本就是对的），但只要用户新增一本书，**损坏的原文就被合法数据覆盖了，再也找不回来**。
- 原因：`loadRecords` 只做了"返回空数组 + 提示"，没有保留原文。
- 影响：与要求里「不要静默覆盖无法解析的旧数据」不完全相符 —— 虽然提示了用户，但数据确实永久丢失。

**问题 4：`CoverImage` 的失败状态不随封面地址变化重置（潜在问题）**

- 现象：同一个组件实例先渲染 A 书（图片 404 → 标记失败），再被复用渲染 B 书（图片有效）时，B 书会错误地显示占位块。
- 原因：失败状态是一个布尔量 `failed`，**不记录"是哪张图失败了"**。
- 影响：**当前不可复现** —— 本项目所有书都是手动录入、都没有 `coverUrl`，走的都是"没有封面"分支，`failed` 根本不会被置为 true。属于同类问题（第一/第四阶段修过的"组件复用导致状态串味"）在封面上的翻版，顺手用最小改动修掉。

**问题 5：同一套业务计算写了两遍**

- 现象 1：`ShelfPage` 自己用 `books.filter(...).length` 数每个状态的数量，而 `lib/stats.ts` 的 `countByStatus` 是同一件事。四个筛选按钮各遍历一次数组。
- 现象 2：详情页路径 `'/books/' + encodeURIComponent(id)` 在首页和书架页各拼一次 —— 这种带编码的拼接一旦哪边漏了 `encodeURIComponent` 就会产生坏链接。
- 影响：规则两处实现，将来改一处漏一处；也带来无谓的重复遍历。

**修复 3 的细节**（唯一一处触及存储逻辑的改动）：

```
const CORRUPTED_BACKUP_KEY = 'readflow:records:v1.corrupted'

function backupCorruptedRaw(raw: string): void {
  try {
    window.localStorage.setItem(CORRUPTED_BACKUP_KEY, raw)
  } catch {
    // 备份失败（存储满 / 被禁用）不影响主流程，用户已通过 readError 收到提示
  }
}

function corruptedResult(raw: string, readError: string): LoadRecordsResult {
  backupCorruptedRaw(raw)
  return { records: [], corrupted: true, readError }
}
```

三种"数据的某些部分不可用"的情况都会走这里：JSON 解析失败、结构不是数组、**以及"解析成功但有记录被丢弃"**。
提示文案也同步加上了「（原文已备份）」，让用户知道数据没有凭空消失。

注意：这**不是**一套新的存储框架 —— 只在已有 `loadRecords` 里多写了一个键，没有改主键、没有改数据结构、没有动 `saveRecords`。

## 五、数据一致性和持久化处理方式

### 5.1 一份数据，一条写入口，一条读入口

```
读：main.tsx → App → useBooks() → useState(loadRecords)
                             ↑ 惰性初始化，同步执行一次，首屏就是真实数据

改：任意页面 → useBooks 的操作（addBook / updateStatus / updateProgress / updateNote / removeBook）
                → commit(next)：
                     latestBooks.current = next   记住最新数组（连续操作不会互相覆盖）
                     setBooks(next)               更新 React 状态 -> 所有页面重渲染
                     saveRecords(next)            同步写 localStorage，并拿到成功/失败
                     返回结果                      页面据此提示，不会把失败说成成功

显示：任何列表/统计都是"渲染时从 books 现算"，不存第二份
```

**没有**在组件里各写一套存储逻辑，**没有**把统计数字写进 localStorage，**没有**在 effect 里无条件重复写入。

### 5.2 读取时的容错策略（本阶段补充了备份）

| 情况 | 处理 | 是否备份原文 |
| --- | --- | --- |
| 键不存在（第一次使用） | 空书架，不提示 | 不适用 |
| localStorage 不可读（无痕模式等） | 空书架 + 「本地存储不可用，本次记录无法保存」 | 不适用 |
| `JSON.parse` 失败 | 空书架 + 提示 + **备份原文** | 是 |
| 解析成功但不是数组 | 空书架 + 提示 + **备份原文** | 是 |
| 解析成功但个别记录不合法 | 丢弃那几条、保留合法的 + 提示 + **备份原文** | 是 |
| 单条记录里某个字段不合法 | 该字段当作没设置，记录仍保留 | 否（数据没丢） |
| `currentPage > totalPages` | 钳到 `totalPages`，维持不变式 | 否 |
| 写入失败（存储满 / 被禁用） | 页面顶部提示条；**不会提示成保存成功** | 不适用 |

**关于备份**：备份键独立于主键（`readflow:records:v1.corrupted`），所以主键被合法数据覆盖后，原始内容仍可人工找回。

### 5.3 跨页面的一致性靠什么保证

**靠"同一份数据"而不是"同步机制"。** 四个页面拿到的都是 `App` 里那一次 `useBooks()` 产出的 `books`；任何操作最终都会替换这个数组的引用，React 重渲染时每个页面各自重算自己要显示的东西。所以不存在"某个页面忘了刷新"的可能，也**不需要**（更不应该）用 effect 去手工同步。

实测覆盖了这些方向：新增 / 改状态 / 改进度 / 改笔记 / 删除 → 首页统计、首页两个列表、书架列表、书架筛选计数、详情页，全部一致。

## 六、阅读进度、笔记及阅读状态的校验规则

### 6.1 阅读进度

| 输入 | 处理 | 实测 |
| --- | --- | --- |
| 当前页 = 0 | **合法**（刚翻开） | 显示 0% |
| 当前页为空 | 合法，表示不设置当前页 | 记录里该字段消失 |
| 当前页为负数 | 拒绝：「当前页数请填 0 或正整数…」 | 已存数据不变 |
| 当前页含小数 / 文字 | 拒绝，同上 | 已存数据不变 |
| 总页数为空 | 合法，表示未知；**不显示百分比** | 显示「已读 X 页（未设置总页数…）」 |
| 总页数 = 0 或负数 | 拒绝：「总页数必须大于 0；如果不知道总页数，请把它留空。」 | 已存数据不变 |
| 当前页 > 总页数 | **阻止保存**并说明具体数字 | 已存数据不变 |
| 当前页 = 总页数 | 合法，100% | 进度条满 |
| 改小总页数导致当前页越界 | 同"当前页 > 总页数"，保存前重新校验 | 已存数据不变 |

**关键点**：

- 校验发生在**保存时**（不是每次按键），失败时**保留用户当前输入**，只提示错误 —— 不会静默替用户改数字。
- 用 `/^\d+$/` 卡格式再 `Number()`，从源头避免 `NaN`、空串、负数、小数、科学计数法进库。
- 百分比**不存储**，由 `computeProgressPercent` 现算并钳制在 0~100；总页数未知时返回 `null`（不用 0 冒充）。

## 十、与本阶段相关的 5 个前端面试问题

**Q1：四个页面都要显示同一份书籍数据，你怎么保证它们永远一致？**

答：**不去"保证"，而是让它们根本不可能不一致** —— 数据只在 `App` 里用 `useBooks()` 取一次，然后通过 props 发给各页面；所有修改都经过 `useBooks` 里唯一的 `commit`：先更新 state、再写 localStorage、再返回结果。state 换了引用，React 重渲染，每个页面各自重算自己要显示的东西（统计、筛选、排序都是渲染时现算的纯函数）。所以不存在"某个页面忘了刷新"，也不需要写 `useEffect` 去手工同步。反过来说，如果每个页面各存一份 `books` `useState`，那才需要一堆同步代码，而且迟早漏一处。

**Q2：这轮修复里有两个问题是"组件被复用了导致状态串味"，能具体讲讲吗？**

答：对，是同一类 bug 的两个实例。
① 详情页：从 `/books/A` 跳到 `/books/B` 时，React Router **不会重新挂载页面组件**，`useState` 的初始值只在首次挂载时算一次，结果 B 书的输入框里残留着 A 书的笔记。解法是给编辑区加 `key={record.book.id}` —— key 变了 React 就当作另一个元素，卸载重建，草稿自然重置。
② 封面：`CoverImage` 里用了一个布尔 `failed` 表示"图片加载失败"。如果这个实例先渲染了 A 书（失败），再被复用去渲染 B 书，B 书就会错误地显示占位块。解法是改成记录"**是哪张图失败了**"（`failedUrl === url` 才显示占位），换 URL 就自动失效。
一句话总结：**组件复用是 React 的默认行为，"实例内部状态"必须和"它当前渲染的数据"绑在一起**，要么用 key 强制重建，要么让状态的语义带上标识。

**Q3：localStorage 里的数据坏了，你的应用会怎样？**

答：分三个层次处理，都不会白屏。
① **解析层**：`loadRecords` 把 `getItem` 和 `JSON.parse` 都包在 try/catch 里，任何异常都转成"空数组 + 一条提示信息"，返回给调用方，应用照常启动。
② **记录层**：解析成功但内容不合法时采取"字段级容错" —— 缺 `id`/`title`、`status` 不是三个合法值之一、缺 `addedAt` 的整条丢弃；而 `currentPage` / `totalPages` / `note` / `finishedAt` 这些可选字段不合法时只是当作"没设置"，**不会因为一个坏字段把整条记录毁掉**；顺手还会把 `currentPage > totalPages` 的越界值钳回 `totalPages`。
③ **不丢原文**：这一阶段刚补的 —— 检测到损坏时把原始字符串另存到独立的备份键 `readflow:records:v1.corrupted`。因为一旦用户接着新增一本书，主键就被合法数据覆盖了，没有备份就真的找不回来了。实测确认：覆盖主键之后备份里仍然是原始内容。

**Q4：表单校验应该写在哪一层？**

答：这个项目里的分工是：**边界做严格校验，领域层信任入参，存储层修复脏数据**。
- **边界（表单）**：`parseProgressInput` 在保存时校验，用 `/^\d+$/` 卡格式，逐条给出具体错误（"总页数必须大于 0；如果不知道总页数，请把它留空"），失败时**保留用户输入**、只改提示。
- **领域层（`applyProgress`）**：只负责"把已经校验过的值写进记录"，不做二次判断（做了也是不可达代码）。
- **存储层**：对外部不可信的 localStorage 数据做字段级容错和不变式修复。
这样分的好处是：用户看到的是**具体原因**而不是被系统悄悄改掉数字；同时又能保证真正落库和重新读回来的数据始终满足 `currentPage <= totalPages` 这类不变式。

**Q5：这轮"检查 + 修复"，你是怎么决定改什么、不改什么的？**

答：我先做全量静态扫描（找 `any` / `console` / 缺 key / 原地改数组），再逐个模块读代码，把候选问题列成一张表，然后按两条标准筛：
- **能不能复现、影响是否真实**。比如"导航栏点进去必然报错"和"想读的书打不开详情页"是能立刻复现的功能死角，必须修；而"统计卡片不可点击"虽然也不理想，但要先把筛选同步到 URL 才能做，属于新功能，就只记下来不改。
- **改动是否最小**。比如封面失败状态那个 bug 当前**根本触发不了**（所有书都没有封面 URL），但因为改动只有 4 行、且和"组件复用串味"是同一类问题，我选择顺手修掉；而"在领域层再加一层钳制"虽然听起来更严谨，实际是永远走不到的代码，就不加。
我也刻意**没有动**任何正常工作的模块（`useBooks`、`stats`、`ReadingEditor`、`BookDetailPage` 一行未改），因为"看起来能更好"不构成改动的理由 —— 每改一处都要重新验证一遍，这个成本要花在真的有问题的位置上。
